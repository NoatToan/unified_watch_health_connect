# Zepp / Amazfit (Huami) connection & session analysis — Zepp 6.10.1

Scope: connection lifecycle, session/context, post-connect basics, robustness, gaps. Auth is treated
as a state-machine call point only; crypto internals are deliberately out of scope. Tags: [V] seen in
decompiled source, [I] inferred, [Ext] public/external. No real-watch/HCI capture exists in this repo.

Paths: `SRC` = `unified_health_app/docs/re-evidence/zepp/jadx-base/sources`;
`DRV` = `unified_health_app/driver/zepp/src/main/kotlin/com/unified/health/driver/zepp`;
`CORE` = `unified_health_app/core/ble/src/main/kotlin/com/unified/health/core/ble`.
Vendor BLE stack is split between `com.xiaomi.hm.health.bt.*` (device/profile/GATT/scan/auth) and
`com.huami.bluetooth.*` (channel/GDSP/auth modules).

## 1. Connection lifecycle end-to-end

Ordering (vendor, main MiLi/Zepp path): scan → select/bind → `connectGatt` → service discovery →
init characteristics → channel version → (v2 only) module list → app auth → set time → settings →
device info → `AUTH_SUCCESS` (ready). [V]

**Scan / select** [V]
- No OS `ScanFilter`: `startScan(null, …)` then software filter (`SRC/com/xiaomi/hm/health/bt/scan/BleScanCenter.java:307`). Bind scans use `filterUUID(FEE0)`, a per-model name list (`HMBindMiLiLogic.java:595,828`), or `filterAddress` for QR (`:797-801`).
- Timing: first scan 20 s (`HMBindMiLiLogic.java:391`), second scan 40 s (`60000 - p`, `:953-956`); QR/address scan 30 s (`:797`). Drop RSSI > 0 or < −90 and non-discoverable adverts; stop early at ≥ −45; first-round accept only ≥ −60 (`:1118,1143-1173`).
- QR carries MAC (and PnP hints) only: `https://api.amazfit.com/app.json?macAddress=…` (`SRC/com/xiaomi/hm/health/device/capturedevice/CaptureQRResultKt.java:15-27,77`). No key in QR.
- Vendors do **not** call `createBond()` on the MiLi/Zepp bind path; the only `createBond` hits are classic/headset features. Driver `bond=false` matches (`DRV/ZeppDriver.kt:51`). [V]
- Device model from advertised name → `HMDeviceSource` (`HMBindMiLiLogic.java:845-869`). Pro devices first query the Huami cloud (`GET binds.json` via `HMDeviceWebAPI.bindDevice`, `HMBindMiLiLogic.java:872-874`), then create `HMMiLiProDevice` with `AuthInfo(randomKey(), isPair=true)` and `create(true)` = direct connect (`:294-304`).

**GATT connect** [V]
- `a0.x()` calls `connectGatt(context, autoConnect=false, callback, TRANSPORT_LE)` (`GattUtils`), arms a 45 s connect timeout whose expiry marks `DISCONNECTED` (`SRC/com/xiaomi/hm/health/bt/gatt/a0.java:1159-1183`, runnable `D()` at `:131-137`).
- `onConnectionStateChange` (status 0 + state 2) → `CONNECTED`; `GattPeripheral.onGattConnected` then calls hidden `refreshGatt(true)` on API ≥ 28 and `discoverServices`, with a 30 s discovery timeout (`SRC/com/xiaomi/hm/health/bt/gatt/GattPeripheral.java:228-249`; timeout runnable `E()` in `a0.java:140-145,795`). This refresh-before-discovery workaround is absent from our core (`CORE/gatt/AndroidGattClient.kt:128-135`).
- `onServicesDiscovered` → `init()` → `initCharacteristics()` → callback → `HMBaseBleDevice.initChannel()` (`HMBaseBleDevice.java:1061-1066,903-927`).

**Channel setup / version** [V]
- `BleChannelLink.linkVersion()` writes `[0x01]` on 0x0016 and waits ≤ 5 s for `[0x02, version, encryptEnable?]` (`SRC/com/huami/bluetooth/profile/channel/model/BleChannelLink.java:252-267`; `GattPeripheral.sendCommandWithResponse` default 5000 ms, `GattPeripheral.java:394-395`).
- version 1 → `BleChannelImpl`/`ChannelApiImpl` (no appId); version 2 → `BleChannelImpl2`/`ChannelApiImpl2` (appId byte) and additionally registers notify on 0x0016 for ACKs (`BleChannelFactory.java:53-66`, `ChannelFactory.java:26-34`, `BleChannelImpl2.java:112-118`).
- On a Huami-OS watch (version ≥ 2, `BleChannelLink.java:205-207`) a failed `initChannel()` is fatal: `INIT_FAILED` + disconnect (`HMBaseBleDevice.java:915-921`); legacy only requires `initCharacteristics`. [V]

**Module list (v2 only)** [V]
- `BuiltInModule` sends `0x03` (if the version reply had an encrypt byte) or `0x00`, expects reply `0x04`/`0x01`, `count u16 LE` then `(id u16, requireEncryption u8)` or `id u8` (`BuiltInModule.java:364-437`); timeout 5000 ms (`BuiltInModule.java:54`). A missing/malformed/trailing-byte list becomes an empty map (`:374-401,407-435`). Cached per MAC in a static map (`:68,352-362`).
- **Correction to the existing brief/docs:** the vendor never queries a module list on channel v1 and `BaseProfile.supportModule()` returns false unless the channel version is exactly 2 (`BaseProfile.java:486-499`; `BuiltInModule.java:365-368`). Therefore v1 watches always take legacy 0x0009 auth; module 0x80 is reachable only on v2 without an `encryptEnable` byte. The driver's "v1 + module 0x80" path (`DRV/ZeppHandshake.kt:61-84`) is not vendor-backed. [V]

**Auth selection** [V]
- `DeviceAuthorizationFactory.createAuthorization()`: if `supportModule(0x80) || supportModule(0x82)` → channel auth; `encryptEnable == null` → `DeviceAuthorizationImpl1` (module 0x80); otherwise `DeviceAuthorizationImpl2` (module 0x82); neither → `TraditionalDeviceAuthorizationImpl` on characteristic 0x0009 (`SRC/com/xiaomi/hm/health/bt/profile/auth/DeviceAuthorizationFactory.java:88-94`).
- Module commands use channel framing; `BaseModule.sendCommand` default timeout 15 s (`BaseModule.java:811-827`), local bind 30 s (`AuthModule.java:569-578`). Session-auth steps are the four 0x82 calls / three 0x80 calls / 0x0009 char exchange already documented; key/session material is produced by `DeviceAuthorizationImpl2.a()` and stored through `EncryptKeyStore` (call point, no crypto detail).

**Post-auth / ready** [V]
- Auth thread: `AUTH_START` → auth → `AUTH_PROTOCOL_SUCCESS` → `setDateTime(2A2B)` → `SET_TIME_SUCCESS` → settings module init (`B`) → `readDeviceInfo()` → `GET_DEVICE_INFO_SUCCESS` → battery registration (`z()`) → `AUTH_SUCCESS` (`HMBaseBleDevice.java:170-258`). `AUTH_SUCCESS` clears the 120 s overall watchdog (`N()`, `:493-498`) and calls `onDeviceConnected()`, which registers the ConnectModule parameter listener and resets GDSP state (`:997-1008`).
- `isConnected()` is true for `AUTH_SUCCESS`, `AUTH_PROTOCOL_SUCCESS`, `AUTH_SUCCESS_WITHOUT_DEVICE_INFO`, `SET_TIME_SUCCESS`, `GET_DEVICE_INFO_SUCCESS` (`HMBaseBleDevice.java:933-939`).
- MTU: the app does **not** call `requestMtu` on the main path. After device info it queries module 0x15 `queryConnectParam` (reply `skip u8, payload u16 LE`; ATT MTU = payload + 3, max 247) and calls `Mtu.setAttMtuSize()` (`MiLiProProfile.java:369-394,2053-2056`; `ConnectModule.java:166-176`; `ConnectionParamCodec.java:56-59`; `Mtu.java:5-35`). Driver instead requests 247 up front via `linkRequirements` (`DRV/ZeppDriver.kt:51`, `CORE/gatt/GattConnector.kt:59-63`).

## 2. Context holding / session state

| Module list + `requireEncryption` | per-MAC static cache in `BuiltInModule.moduleListCached`; per-MAC `ChannelModuleStore` (`BuiltInModule.java:68,352-362`; `ChannelModuleStore.java:25,41-52`) | per-session `modules: Map<Int,Boolean>` loaded after version (`ChannelTransport.kt:61-104`); encryption rule `version.encryptEnable && modules[module]` (`:245-246`) |
| Nonces/key state | `EncryptKeyStore` keeps key, local nonce `r0`, remote nonce `r1`; `r0` increments per encrypted send, `r1` accepted within a 100 000 window (`EncryptKeyStore.java:28-44,69-81`) | equivalent nonce/key state inside `ChannelCipher`, per session; no persistent keystore |

- **Reconnect/backoff:** `GattPeripheral.g0()` cleans up, waits 2 s, then `x()` reconnect when `autoReconnect` and the adapter is on (`GattPeripheral.java:111-126`); no attempt cap/backoff. Status 133/255 increments a fail count; at ≥ 2 it switches to scan-based reconnect only if `SUPPORT_RE_CONNECT_WITH_SCAN` (default **false**) and a bridge exists (`:63-65,269-277`; `HMBleConfig.java:15`). `BluetoothSwitcher` can toggle the adapter, but `SUPPORT_AUTO_RESTART_BT` is default false, so GATT-operation timeouts instead surface `ISBEListener.onException` → user notification (`BluetoothSwitcher.java:20-84`, `BraceletApp.java:625-629,1190-1196`).
- Our app already has an event-driven keeper with exponential backoff 2 s → 2× → … capped 5 min, link-loss reconnect, and a `connectedDevice` foreground service (`unified_health_app/core/data/src/main/kotlin/com/unified/health/core/data/link/DefaultDeviceLinkKeeper.kt:60-102`; `unified_health_app/app/src/main/AndroidManifest.xml:96-99`; `unified_health_app/app/src/main/kotlin/com/unified/health/sync/DeviceSyncService.kt:34-84`). Vendor equivalent is a resident `HMCoreService` foreground service with `START_FOREGROUND`/`STOP_FOREGROUND`/`KEEP_ALIVE` actions (`unified_health_app/docs/re-evidence/zepp/jadx-base/resources/AndroidManifest.xml:480-499`; `HMCoreService.java:904-921,1195-1233`).
- **Keepalive/heartbeat:** live HR re-sends `KEEP` every 10 s until stopped (`HMHeartRateController.java:193-202`); channel has no transport-level heartbeat — link liveness is GATT/connection-based.
- **Multi-device:** vendor holds one `HMBaseDevice` per `HMDeviceType`; major-device priority is MILI > WATCH > SENSORHUB > SHOES > WEIGHT (`HMDeviceManager.java:290,1555-1562`). Our core serializes one active link (`MultiVendorDeviceConnection.active`), so vendor-style watch+accessory concurrency is absent by design.

## 4. Robustness behaviors worth copying

1. **Overall connection watchdog — 120 s.** Armed on any connecting/scanning/discovery/init/auth state, cleared on `AUTH_SUCCESS`; expiry yields `CONNECTING_TIMEOUT` (`HMBaseBleDevice.java:109-110,511-523,887-900,493-498`). Our driver has per-step timeouts but no whole-handshake deadline.
2. **Layered stage timeouts.** connectGatt 45 s; service discovery 30 s; each read/write/descriptor operation 30 s (`a0.java:1165,795,327-517`). Our core uses 20 s connect, 20 s discovery, 10 s per GATT op (`CORE/gatt/AndroidGattClient.kt:295-296`, `GattConnector.kt:162-165`). Vendor's per-op budget is more forgiving for slow Huami firmware.
3. **Serialize every GATT operation** on a single-thread executor and block on a condition, so Android never receives concurrent GATT calls (`a0.java:64-67,321-517`); our `AndroidGattClient.operationLock` already does the coroutine equivalent (`:52,275-290`).
4. **Treat `GATT_CONNECTION_CONGESTED` (143) as success** for read/write/descriptor, returning 0 instead of failing (`a0.java:566-573,953-961,1149-1157`). Risky but pragmatic for Huami stacks; validate before copying.
5. **Refresh the GATT cache on API ≥ 28 after every connect, before discovery** (`GattPeripheral.java:235-249`; reflection in `a0.refreshGatt` `:994-1008`). This is a common fix for stale service/status-133 failures and is missing in our connector.
6. **Fast direct reconnect:** cleanup → 2 s → reconnect, unlimited; scan-based reconnect reserved for repeated 133/255 and disabled by default (`GattPeripheral.java:111-126,63-65,269-277`). Our exponential backoff (2 s…5 min) is safer for battery/Android; vendor shows the value of a short first retry.
7. **Channel send serialization + ACK window:** one whole message at a time behind a `Mutex` (`ChannelApiImpl2.transport` `:239-313`); NEED_REPLY on every 16th packet and on the last packet (`ChannelRequest.REPLY_FREQ=16`, synthetic defaults `ChannelRequest.java:14,120`; `BaseChannelApiImpl.packetRawData` `:741-769`); v1 reply timeout 5 s; v2 declares 15 s (`BaseChannelApiImpl.java:61`; `BleChannelImpl2.java:32`); packet index mod 256; session/packet/size/module errors answered with codes 1–5 (`BaseChannelApiImpl.java:633-657`). Driver mirrors the split/ACK rules but waits 15 s on v1 too (`ChannelTransport.kt:161-173`). The v2 send loop body is a jadx gap (`BleChannelImpl2.java:214-222`, `BaseChannelApiImpl.java:598-606`), so retry-on-ACK-timeout remains unknown.
8. **GDSP integrity + retry:** control 5 s, header 20 s, data wait 20 s (`HMProSyncDataBaseProfile.java:145-147,405-406,449-462`); per-packet `(last+1)%256` check (`:159-177`); CRC32 of the whole payload (`GDSPApiImpl.java:112-150`); stop `[0x03, code]` always sent (`GDSPSyncTask.java:116-119`). `CommonGdspSyncTask` retries the whole sync up to 3 times on failure (`CommonGdspSyncTask.java:102-157`; default `BaseGdspSyncParam.java:53`). Our driver verifies sequence+CRC but aborts the type on first failure and never retries (`DRV/ZeppSession.kt:128-160`).
9. **Live-HR watchdog:** re-issue KEEP every 10 s and keep measuring even if one KEEP fails (`HMHeartRateController.java:193-202`; `DRV/ZeppOsLiveHeartRate.kt:40-50` already matches).
